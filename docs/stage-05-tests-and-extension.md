# 阶段 5 · 用失败场景检查工程，再考虑扩展

> 代码快照：`stage-5`。上一阶段：`stage-4`。

## 一、本阶段目标

能用自动化测试解释工程的边界，并知道增加功能时应该修改哪一层。

## 二、新引入的概念

**单元测试与集成测试** 解决不同问题。纯引擎测试检查数值边界和图结构；真实 PostgreSQL 测试检查事务、锁、约束和重连后的持久化。用内存 mock 通过，并不能证明行锁有效。

**业务不变量** 是系统任何时刻都必须成立的约束：同一实例最多一个待办；只有指定人能审批；旧版本实例不随新草稿改变；已完成任务不能再次完成。这些比某个按钮的 CSS 类名更值得测试。

**扩展边界**：增加控件需要改模型与表单渲染；增加自动节点需要改图校验、引擎和审计；增加登录需要把演示身份替换成可信会话，而不是仅隐藏用户下拉框。

## 三、按这个顺序阅读代码

1. `packages/bpm-core/test/engine.test.ts`：从 3000 临界值测试进入引擎。
2. `apps/api/test/bpm.test.ts` 的 fixture：确认连接 `_test` 数据库，理解为什么每个用例先重置数据。
3. 并发审批用例：两个 Promise 同时请求同一个 Task，对照 service.act 的 FOR UPDATE。
4. 快照隔离用例：对照 save/publish/start 的三个复制时机。
5. 重连与唯一索引用例：观察数据库约束如何兜住应用错误。
6. HTTP 用例：从 401/400/403/409 返回码追到控制器、过滤器和业务服务。
7. `scripts/check-comments.mjs` 与格式化配置：阅读约定如何自动检查。
8. 最后再读 [全局架构](architecture.md) 与根目录 `overview.md`，整理自己的系统图。

**重点**：先提出一个会失败的场景，再选合适测试层级。不要把实现一字不差抄进测试当作“覆盖”。

## 四、如何验证与练习

```powershell
pnpm db:up
pnpm typecheck
pnpm test
pnpm format:check
pnpm comments:check
pnpm build
```

预期全部通过。集成测试只操作 `bpm_test`，页面中的 `bpm` 数据保持不变。

练习一：扩展一个 checkbox 字段，列出要动的模型、校验、设计面板和渲染器。练习二：实现审批撤回之前，先写“旧任务如何失效、新待办如何创建、历史如何保存”的状态表。练习三：为并行审批列出 token、汇聚与多人完成策略，说明为何不能只允许一个节点多接几条出线。

## 五、常见问题

- **测试连接到业务库怎么办**：测试初始化会拒绝数据库名不以 `_test` 结尾的 URL。不要为了通过测试移除此保护。
- **改了 JSON 配置却没有注释**：JSON 不支持注释，集中看 `docs/configuration.md`；锁文件和生成文件也不应手改。
- **为什么暂时没有会签、退回和 BPMN 导入**：当前引擎是串行有向无环图，支持数字条件分支；复杂语义需要先调整模型、执行器和任务约束，再增加 UI。
- **这是原 aiflow 的源码吗**：只参考它的 apps/packages 分层、独立引擎和发布快照思路。本项目代码独立编写，没有修改参考项目。
