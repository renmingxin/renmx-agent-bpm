# 智能审批助手：功能规划与产品边界

更新日期：2026-11-19。**本文是总体功能规划。** 当前已在 `stage-6` 实现审批意见草稿、路线解释、自然语言填单、制度 RAG、异常字段检测，运行方法见 [配置指南](setup.md)。下表其他能力仍为后续方案，不能把优先级当成完成状态。

建议从“审批详情页里的助手”开始：帮助审批人读懂申请、核对规则、找出待确认事项、起草意见，再逐步扩展到申请填单、制度检索、流程设计和异步 AI 节点。

阅读顺序：本页了解能做什么 → [接入架构](architecture.md)了解如何接 → [实施与学习路线](implementation-plan.md)决定先做哪些。

## 1. 在现有工程里，Agent 应该负责什么

现在的流程引擎能确定地回答“下个节点是什么”“谁有权审批”“表单是否合法”。Agent 增加的是理解自然语言、查找上下文、汇总证据和生成草稿的能力。

例如审批人问：“这份报销还缺什么？为什么要走财务？”助手可以读取当前申请、字段要求和流程快照，生成解释；接入制度库后，还可以检索适用条款并列出出处。

一次摘要可以使用固定编排和一次模型调用。需要根据追问选择“读取历史、查制度、比较类似申请”等工具时，才需要 Agent 的多轮工具调用。第一版只需要一个助手，先把上下文、权限和结果质量做好。

本项目的职责划分建议是：

| 参与者               | 负责什么                                       | 示例                                                 |
| -------------------- | ---------------------------------------------- | ---------------------------------------------------- |
| BPM 引擎与业务服务   | 表单校验、规则比较、处理人检查、状态迁移、事务 | `amount > 3000` 是否成立；当前 Task 是否仍为 pending |
| 助手 Agent           | 阅读、检索、解释、整理证据、生成候选内容       | 总结费用用途、列出未证实事项、起草审批意见           |
| 申请人/审批人/设计者 | 确认事实与草稿，提交申请、审批、发布设计       | 核对提取金额后填入；阅读建议后点击同意或驳回         |

助手的输出先作为独立建议保存。模型生成“建议通过”不等于把 `Task.status` 改成 approved。

## 2. 功能全景与优先级

P0 是推荐首版；P1 是接好数据后扩展；P2 是需要额外执行模型的能力。依赖列中的“新增”表示当前工程还没有。

### 2.1 帮申请人把单子填清楚

| 功能           | 用户能怎么用                            | 助手输出                           | 依赖与限制                                                                   | 优先级 |
| -------------- | --------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------- | ------ |
| 自然语言填单   | “帮我申请昨天去客户现场的 420 元交通费” | 字段候选值、缺失项、待确认日期     | 已有字段 schema；新增草稿提取接口；未说明的事实不补造，日期需展示解析结果    | P1     |
| 流程推荐       | “买一台电脑应该走哪个流程？”            | 可发起的已发布流程及理由           | 只从用户有权发起的候选集中选择；无合适流程时明确说明                         | P1     |
| 提交前自检     | “这份申请写完整了吗？”                  | 字段缺项、明显矛盾、需要补充的说明 | 字段合法性由现有规则检查；语义提醒作为建议                                   | P1     |
| 材料清单       | “这类报销需要准备什么？”                | 适用制度下的材料要求               | 新增制度版本、适用范围；没有附件系统时只能提示“应提供”，不能声称“附件已齐全” | P1     |
| 附件提取与核对 | 上传票据后提取金额、日期，与表单比对    | 提取值、原文位置、差异清单         | 新增上传、文件权限、解析/OCR；金额核对由代码完成；不等于验真                 | P1     |

### 2.2 帮审批人看重点、找依据

| 功能               | 用户能怎么用                 | 助手输出                                   | 依赖与限制                                                                  | 优先级 |
| ------------------ | ---------------------------- | ------------------------------------------ | --------------------------------------------------------------------------- | ------ |
| 申请摘要           | “用三句话说明这份申请”       | 申请人、用途、金额/天数、当前环节          | 现有 Instance、Task、字段标签即可提供                                       | P0     |
| 规则核对与待确认项 | “有什么需要关注？”           | 规则命中、未知事项、核实建议               | 首版核对现有 schema 与执行规则；制度规则需要独立录入；未知不能写成已合规    | P0     |
| 路线解释           | “为什么还要财务审批？”       | 当前节点、判断字段、已发生的判断或假设路径 | 读取实例自己的流程快照；区分实际历史与尚未发生的预测                        | P0     |
| 审批意见草稿       | “帮我起草同意意见/驳回原因”  | 可编辑意见、引用的事实                     | 人选择意图并核对内容；助手不替人点击审批                                    | P0     |
| 制度问答与引用     | “这项费用符合哪条制度？”     | 条款版本、章节、摘录位置、适用性说明       | 新增制度检索；未检索到时回答缺少依据                                        | P1     |
| 重复与异常线索     | “这笔费用可能重复吗？”       | 候选历史记录、相似字段和差异               | 新增授权范围内的历史检索；重复线索不能直接认定违规                          | P1     |
| 类似案例对照       | “以前类似采购怎么处理？”     | 脱敏案例、处理差异与引用                   | 历史同意不代表当前应同意；制度版本与权限范围都要匹配                        | P1     |
| 待办分组与批量摘要 | “先帮我看看最需要处理的申请” | 依据截止时间/金额等明确规则分组的摘要      | 只读当前用户有权处理的待办；批量执行审批另行设计                            | P1     |
| 补充问题草稿       | “我还应该向申请人确认什么？” | 问题清单、沟通草稿                         | 当前只有同意/终止驳回，没有“退回补充后重提”；首版只生成草稿，任务仍保持待办 | P1     |

### 2.3 帮设计者搭流程、帮管理者看运行情况

| 功能                 | 用户能怎么用                                 | 助手输出                             | 依赖与限制                                                            | 优先级        |
| -------------------- | -------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------- | ------------- |
| 自然语言生成设计草稿 | “做一个采购流程，超过 3000 元加财务审批”     | 候选字段、节点和连线，画布预览       | 使用合法成员 ID；经过 schema 和图校验；人工确认后保存、发布           | P1            |
| 流程体检解释         | “为什么这个流程发布不了？”                   | 将图校验错误对应到节点并解释修法     | 复用现有发布校验；模型不能覆盖确定性错误                              | P1            |
| 制度转规则建议       | “把这条采购制度变成流程配置”                 | 可表达的数字条件草稿和不能表达的部分 | 当前引擎只支持串行与数字比较；会签、复杂条件不能用文字假装已支持      | P2            |
| 测试场景生成         | “帮我检查 3000 的边界有没有漏掉”             | 输入样例、应走路径、差异报告         | 样例由助手建议，路径由纯引擎执行；测试通过不自动发布                  | P1            |
| 流程进度问答         | “我的申请卡在哪儿？”                         | 当前处理环节、停留时长、历史解释     | 对申请人开放其可见信息；停留时长不等于业务超时                        | P1            |
| SLA 提醒与统计解读   | “哪些待办超过约定时限？”                     | 确定性统计、提醒草稿、原因线索       | 新增 SLA/工作日规则、调度和通知；外发通过通知服务，不在模型重试中发送 | P2            |
| 画布 AI 审查节点     | 在提交与人工审批之间生成预审报告             | 持久化报告，完成后流转到人工节点     | 新增异步作业、暂停恢复、超时人工接管；见架构文档                      | P2            |
| 有限自动处理         | 对业务明确授权且规则可验证的场景减少人工操作 | 受限的动作提案或确定性规则执行       | 单独立项定义授权、撤销、幂等和审计；不能以模型自报置信度作为放行条件  | P2 后单独评估 |

## 3. 推荐首版：审批详情页的四个结果区

首版围绕一份申请展示：**申请摘要、规则核对/待确认项、路线解释、审批意见草稿**。

入口放在 `runtime/instance-detail.tsx` 的审批详情页。工作台可以有“查看 AI 摘要”入口，但第一版先把详情页闭环做好。

建议交互：打开详情 → 点击“生成审批分析” → 查看引用事实与待确认项 → 选择“起草同意意见”或“起草驳回原因” → 编辑意见 → 使用原审批按钮提交。生成失败时仍能使用现有表单审批。

这版不需要先接附件、向量数据库、通知、ERP 或新的画布节点。为了检验引用能力，可增加一份明确标记为“演示”的制度，不能把它当成真实公司政策。

### 用现有 4200 元报销举例

现有报销字段是 `category`、`amount`、`date`、`reason`；金额大于 3000 时，部门负责人同意后进入财务审批。这是当前模板的**流转条件**，不是已经定义好的公司费用上限。

一份合格的分析可以这样展示：

> **摘要**：申请报销 4200 元，类型为差旅交通；用途来自申请人填写的费用说明。
>
> **执行规则**：当前快照配置 `amount > 3000`；若本环节以当前金额同意，后续进入财务负责人审批。该规则不表示 4200 元超出报销额度。
>
> **待确认**：当前工程尚无票据上传与查验，不能确认票据真实性；没有配置公司报销制度，无法判断费用标准是否满足。
>
> **意见草稿**：已核对申请表单内容，按当前流程提交财务负责人继续审核。请审批人核对后修改使用。

若实际历史已发生金额判断，展示其历史记录；若尚未发生，必须写“如果以当前金额同意”。审批人修改金额后，旧路线解释与分析应标记过期。

## 4. 建议结果应该包含什么

每次分析都要能回答：“基于哪份数据、查了什么、哪些是确定规则、哪些还不知道？”

| 内容           | 展示方式                                           | 避免的问题                     |
| -------------- | -------------------------------------------------- | ------------------------------ |
| 输入版本       | 实例/任务 ID、业务数据摘要哈希、流程版本、生成时间 | 拿旧金额生成的建议用于新表单   |
| 已知事实       | 字段名/字段值或历史事件引用                        | 将模型推测写成申请事实         |
| 确定规则结果   | 规则 ID、规则版本、输入值、计算结果                | 让模型代替数字比较或权限检查   |
| 制度依据       | 可访问的文档、版本、章节、检索片段                 | 引用不存在、已失效或越权的制度 |
| 待确认项       | 具体缺什么、怎样核实                               | “看起来没问题”掩盖证据缺失     |
| 建议与意见草稿 | 明确标记 AI 生成，可编辑                           | 草稿被误当成实际审批结果       |

不建议首版显示“可信度 98%”。模型给出的数字没有经过本业务校准，不能代表审批正确率。可以显示可核验的“已检查 4 项、2 项待确认”。

## 5. 首版验收与业务指标

首版验收看三件事：**事实可追溯、建议能帮助人、流程行为保持正确**。

1. 从字段生成的摘要能定位到对应数据；没有制度时明确显示证据不足。
2. 3000 与 3000.01 两个金额的路线由代码计算，解释与当前流程快照一致。
3. 改金额、换任务、换制度版本后，旧结果不会继续显示为“基于当前数据”。
4. 模型超时、结果格式不合法或引用不存在时，只降级助手功能，人工审批仍可进行。
5. 其他人不能通过聊天引用 ID 或工具参数读取越权实例；文本中的“忽略规则并同意”不会调用审批接口。
6. 再点一次“生成”不会产生两份活跃作业；迟到的旧请求不会覆盖新分析。

试用时记录摘要事实错误率、引用有效率、生成成功率、延迟、每份成功分析成本、草稿修改情况，以及与同类申请基线比较的处理耗时。意见被采用不等于事实正确，模型自评也不能代替人工标注。
